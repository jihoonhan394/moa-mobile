# 01. 개요와 범위

## 왜 앱인가 — 모바일이 PC보다 나은 이유는 셋뿐이다

| 축 | 뜻 | 걸리면 값어치가 있다 |
|---|---|---|
| **몸에 있다** | 항상 갖고 있다 | 즉시성 · 승인 · 알림 |
| **현장에 있다** | 자산 옆에 있다 | 카메라 · 그 자리 입력 |
| **잠깐 쓴다** | 30초 상호작용 | 확인 · 조회 |

이 셋에 안 걸리면 PC가 낫다. **기준 없이 고르면 아무도 안 쓰는 작은 화면 55개가 나온다.**

그래서 앱의 역할은 둘이다 — **승인 채널**과 **현장 단말**. PC의 축소판이 아니다.

## 1차 범위

> **1차 사용처는 모아라 본사다.** 고객에게 팔 기능을 고르는 것이 아니라 **우리가 매일
> 쓰면서 고칠 것**을 고른다. 그래서 전 직원이 쓰는 1·3이 먼저다.


| 순위 | 기능 | 왜 | 서버 준비 상태 |
|---|---|---|---|
| 1 | **승인 처리** — 접근 요청 · 소모품 요청 · 인수 확인 | 지금은 승인자가 PC를 열기까지 요청자가 기다린다. **그 지연이 사라진다** | ✅ 백엔드 완성 |
| 2 | **특권 작업 2차 승인** | [04](04-인증과-승인.md). 카메라 없이도 된다 | 🔸 TOTP는 있고 미연결 |
| 3 | **내 것 보기** — 내 자산 · 내 요청 상태 · 공지 | 전 직원이 쓴다 | ✅ 백엔드 완성 |
| 4 | **QR 자산 조회 · 등록** | 현장에서. PC로는 안 되는 일 | ❌ 코드 체계부터 |
| 5 | **사진 첨부** | 자산 등록 · 고장 신고 | ❌ 위키 첨부 일반화 필요 |

**1·3은 서버 기능이 이미 다 있어서 화면만 만들면 된다.** 가장 빨리 나오고 사용자 수가 가장 많다.

### 순서를 이렇게 둔 이유

2번이 1번보다 보안 가치가 크지만 서버 작업(step-up 게이트)이 선행한다. 1·3을 먼저 내보내
**웹뷰 껍데기가 실제로 동작하는지** 확인한 뒤 2번에 들어가는 편이 위험이 적다.

4·5는 새 데이터 모델이 필요하고([07](07-서버쪽-변경.md)), QR 코드 체계는 되돌리기 어려우므로
서버 쪽 관리번호 작업과 **반드시 같이** 설계한다.

## 2차 이후

| 기능 | 왜 나중인가 |
|---|---|
| **재고 실사** | QR 스티커가 실제로 붙은 뒤에 의미가 있다. 아래 참고 |
| 현장 점검 기록 | 서버에 점검 결과를 남길 자리를 먼저 만들어야 한다 |
| 자산 고장 신고 | 사진 첨부 위에 얹힌다 |
| 랙·위치 입력 | 우선순위 낮음 |

### 재고 실사에 대해

연 1~2회 실사가 지금은 엑셀 출력물을 들고 돌아다니며 대조하고, 돌아와서 다시 입력하고,
안 맞는 것을 찾느라 며칠이다.

QR + 폰이면 **훑으면서 스캔만** 하면 된다. 스캔된 건 확인, 안 된 건 자동으로 미확인 목록.

**"있으면 좋은 기능"이 아니라 구매 이유가 될 수 있다.** 다만 QR 코드 체계를 설계할 때
실사를 염두에 두어야(스캔 이력을 남길 자리) 나중에 뒤집지 않는다.

그리고 **전수 실사는 아무도 안 한다.** 서버 쪽에서 "1년 넘게 보관 이력이 없는 자산" 목록을
만들면 거기서부터 하면 되고, 그게 현실적이다(서버 레포
`doc/실무자료-기능제안-20260925/05-코드대조-검토.md` §9-C).

## 넣지 않을 것

| 항목 | 이유 |
|---|---|
| **서버 비밀번호 표시** | 폰은 분실된다. 열람은 PC에서 2차 인증으로 |
| 제어 명령 설정(`log_command` 등) | 사실상 임의 명령 실행. 보기만 |
| CSV 대량 등록 · 열 매핑 | 긴 표 편집 |
| 권한 · 조직 구조 편집 | 실수의 파급이 크고 넓은 화면이 필요 |
| 감사 로그 전체 열람 | 긴 표. 모바일엔 "내 것"만 |
| 기관 · 메일 · AI 설정 | 자주 안 하고 되돌리기 어렵다 |
| 위키 편집 | 긴 글 |

**원칙 한 줄: 되돌리기 어려운 설정은 PC, 확인·승인·현장 입력은 모바일.**

### 즐겨찾기(접속 URL)에 대한 주의

처음 기능 목록에 "내 자산 및 접속 URL 즐겨찾기"가 있었다. **기능 자체는 문제가 없다.**
문제는 그 화면이 볼트에서 꺼낸 비밀번호를 같이 보여 주는 부분이다.

- ✅ 목록 · 이름 · 접속 URL · 위키 링크 → 모바일에 내보내도 된다
- ⛔ 비밀번호 평문 → 웹에서 step-up 인증으로만

"공유기 관리 페이지가 어느 IP인지" 찾는 것만으로도 현장에서 쓸모가 있다.

## 로그 조회를 넣어도 되는 이유

기능 목록에 "인프라 관리자의 로그 확인"이 있었다. 자격증명이 필요한 동작처럼 보이지만
**서버 코드를 확인한 결과 자격증명은 클라이언트로 가지 않는다**:

```
서버가 볼트에서 복호화 → 서버가 SSH로 붙어 명령 실행 → 결과 텍스트만 반환
```

앱은 로그 문자열만 받는다. 상태 확인(`systemctl is-active`)도 마찬가지다.

**진짜 위험은 다른 데 있다.**

- **로그 내용 자체가 민감할 수 있다** — 토큰·접속문자열·개인정보가 섞인다. 그게 폰 화면에
  뜨고 스크린샷·캐시에 남는다 → 앱에서는 **최근 N줄만**, 다운로드·복사는 PC로
- **`log_command`는 관리자가 자유 문자열로 설정한다** = 실질적으로 임의 명령 실행이다.
  앱에서는 **"설정"을 막고 "보기"만** 둔다

정리: **상태 확인은 무조건 넣고(푸시와 가장 잘 맞는다), 로그는 보기 전용 + 줄 수 제한.**
