# 04. 인증과 승인

## 로그인 — 서버의 세션을 그대로 쓴다

서버는 **2단계 진입**이다: 기관 코드 → 이메일·비밀번호. 웹뷰가 그 화면을 그대로 쓰므로
**앱에 추가 인증 계층이 없다.**

앱 UX만 하나 손본다: **기관 코드를 기기에 저장**해 두고 2단계 진입을 첫 실행 때만 보여 준다.
이후에는 이메일+비번 한 화면이다.

> 로그인 식별자는 **이메일**이다(`username`은 표시용). 서버 `MoaUserDetailsService` 참고.

## 왜 인증을 내부망 서버에서 처리하나

| | |
|---|---|
| ① | **인증을 두 곳에 두면 정책이 갈라진다.** 로그인 잠금(계정 5회/출발지 20회)·실패 감사·2단계 진입·기관 스코프가 전부 내부망 서버에 있다. 중계에 또 만들면 그것들이 거기엔 없다 |
| ② | **중계가 비밀을 보게 된다.** DMZ에 비밀번호가 지나가는 지점을 만들 이유가 없다 |
| ③ | **웹뷰라면 추가 작업이 0이다** |

# 특권 작업 2차 승인 (대역 외 step-up)

**이 기능이 앱의 주된 명분일 수 있다.** 카메라가 필요 없어서, 카메라를 막는 기관에서도
값어치를 갖는다.

## 무엇인가

```mermaid
flowchart LR
  A["PC<br/>자격증명 열람 클릭"] --> B["폰 알림<br/>대상 · 요청 IP"]
  B --> C["화면의 숫자 고르기"]
  C --> D["지문 또는 코드"]
  D --> E["PC에 비밀번호 표시"]
```

## step-up과 승인을 구별한다

| | step-up (2차 요소) | 승인 (권한 분리) |
|---|---|---|
| 뜻 | **내가 나임을** 한 번 더 증명 | **다른 사람이** 허락 |
| 예 | PC에서 볼트 열람 → 내 폰에서 통과 | 재기동 → 팀장이 승인 |
| 서버 상태 | `TwoFactorService.verify` 있음, **미연결** | `AccessApprovalService` 완성 |
| 감사 액션 | `STEPUP_PASS` | `APPROVAL_GRANT` |

섞어 기록하면 나중에 "본인이 한 건가 승인받은 건가"를 구별할 수 없다.

## ⚠️ MFA 피로 공격을 반드시 막는다

*"승인하시겠습니까? [예/아니오]"* 만 띄우면 이렇게 뚫린다.

```
공격자가 훔친 비번으로 로그인 시도
  → 내 폰에 승인 요청이 계속 뜬다
  → 짜증나서 또는 실수로 승인 → 끝
```

실제로 Uber(2022)와 Cisco가 이 방식으로 침해됐다. 그래서 **번호 대조(number matching)**:

```
PC 화면:  "폰에서 [ 47 ]을 선택하세요"
폰 화면:  [ 12 ]  [ 47 ]  [ 83 ]
```

공격자는 PC 화면을 못 보니 숫자를 모른다. **사용자 입장에서는 버튼 하나 누르는 것과 거의
같은데 공격은 막힌다. 처음부터 이렇게 만든다** — 나중에 바꾸면 사용자 습관을 바꿔야 한다.

함께 넣을 것:

- **맥락 표시** — 무엇을(`dev-web-01 자격증명 열람`), 어디서(요청 IP·PC), 언제.
  "승인하시겠습니까?"만 뜨면 무의식으로 누른다
- **짧은 만료** 60~120초, 1회용
- **거절하면 그 세션을 즉시 끊고** 관리자에게 알림. 거절은 "지금 누가 내 계정을 쓰려 한다"는 신고다

## 어디에 걸 것인가 (기관이 선택)

| 작업 | 기본값 |
|---|---|
| 자격증명 열람 | ✅ 요구 |
| 솔루션 정지·재기동 | ✅ 요구 |
| 권한 부여 | ✅ 요구 |
| 퇴사 처리(일괄 회수) | ✅ 요구 |
| 솔루션 상태·로그 조회 | ❌ |
| 자산 조회·등록 | ❌ |

**전부 켜면 아무도 안 쓴다.** 기본값을 두고 기관이 조정한다(서버의 `FeatureModule` 자리).

**유효 시간**: 한 번 통과하면 N분(기본 5분) 재요구하지 않는다. 자격증명 3개 보려고 폰을
세 번 들게 하면 사람들이 우회로를 찾는다.

**감사에 네 가지를 다 남긴다**: 요청 · 통과 · 거절 · 만료. 특히 **거절과 만료**가 공격 탐지 신호다.

## 폰이 없을 때 — 폴백을 먼저 정한다

볼트 열람에 폰 승인을 필수로 걸면 **폰 분실 = 업무 정지**다. PAM에서 치명적이다.

**가장 좋은 폴백은 이미 있다.** TOTP 시크릿은 Authenticator 앱(구글·MS)에 있으니
**우리 앱이 없어도 6자리 코드는 나온다.**

```
편한 경로:    PC에서 요청 → 폰 앱에서 번호 대조 승인
항상 열린 길: PC에서 Authenticator 코드 6자리 직접 입력
```

**두 경로를 다 열어 둔다.** 이렇게 하면 폐쇄망(푸시 없음)·폰 분실·앱 미설치가 전부 같은
방법으로 해결된다. 추가로 일회용 백업 코드 10개.

# 인증 방식 세 가지

| 방식 | 설명 | 폐쇄망 |
|---|---|---|
| **TOTP** (기본) | Google Authenticator 방식 6자리 | ✅ 외부 통신 없음 |
| **지문·얼굴** | 폰 보안칩에 키를 만들고 생체로 그 키를 쓰게 함 | ✅ 외부 통신 없음 |
| **인증 제품** | 고객사가 지정한 FIDO 제품 연동 | 고객사 인프라 필요 |

## 생체인증 — 두 가지를 구별해야 한다

| | (A) 로컬 잠금 해제 | (B) 하드웨어 키 + 생체 |
|---|---|---|
| 방식 | `BiometricPrompt` → true/false | Secure Enclave 키로 nonce 서명 |
| 서버가 받는 것 | "통과했습니다"라는 **앱의 말** | 검증 가능한 **서명** |
| 루팅·후킹 | **우회 가능** | 키를 꺼낼 수 없음 |
| 판정 | **비추** | **추천** |

**(B)는 FIDO 서버가 필요 없다.** 서버가 하는 일은 nonce 발급 + 서명 검증뿐(≈200줄).
FIDO2/WebAuthn이 복잡한 것은 *아무* 인증기가 *아무* 사이트와 동작하게 하려는 것인데,
여기는 우리 앱이 우리 서버에 인증하는 1자 관계다.

### 반드시 켤 설정 둘

**① 생체 등록 변경 시 키 무효화**

```
Android: setInvalidatedByBiometricEnrollment(true)
iOS:     .biometryCurrentSet   (.biometryAny 아님)
```

안 켜면 **남의 지문을 추가 등록해 우회**할 수 있다. 기본값이 아니라 명시해야 한다.

**② 서명 대상에 번호 대조 값을 묶기**

고른 번호를 서명 밖에서 따로 보내면 후킹으로 바꿀 수 있다.

```
서명 대상 = 요청ID || nonce || 사용자가_고른_번호 || 행위코드
```

### 포기하는 것

표준 FIDO2의 기기 증명(attestation)과 **"FIDO 인증 제품" 서류 요건**. Android Key
Attestation / iOS App Attest로 하드웨어 보증은 받을 수 있지만 손이 더 간다. 조달 요구사항에
인증 제품이 들어오는 고객은 `FIDO_CERTIFIED` 플레이버로 갈아 끼운다.

### 폐쇄망에서는 TOTP보다 낫다

| | TOTP | 하드웨어 키 |
|---|---|---|
| 외부 의존 | 없음 | 없음 |
| **시계 동기** | **필요**(±30초, NTP 없으면 전원 실패) | **불필요** |
| 피싱 내성 | 약함 | 강함(nonce가 요청에 묶임) |
| 폰 없이 | ✅ Authenticator | ❌ |

**생체는 TOTP를 대체하지 않는다.** 키는 기기를 떠날 수 없으니 새 폰 = 새 키이고, 재등록을
인증할 수단이 TOTP다. 생체는 위에 얹히는 편의 계층이다.

서버는 **사용자별 등록 기기 목록**을 갖고, 사용자가 잃은 폰을 스스로 폐기할 수 있어야 한다.
