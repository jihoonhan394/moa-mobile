# 03. 빌드와 환경

납품처마다 환경이 제각각이다(국방부·공사). **기능을 소스에 박으면 납품마다 포크가 생기고
그게 제품을 죽인다.** 그래서 환경을 빌드 변수로 흡수한다.

기존 `kogas` 프로젝트의 `secure_config.gradle` 패턴을 그대로 쓴다 —
`applyXxxConfig(flavor, vendorType)`가 ① `buildConfigField` ② `sourceSets` 교체
③ 벤더 SDK 의존성을 한 번에 처리하는 방식.

## 축과 값

```groovy
applyNetworkConfig(it, "DMZ_RELAY" | "INTRANET")
applyQrConfig     (it, "CAMERA"    | "NONE")
applyPushConfig   (it, "FCM"       | "NONE")
applyAuthConfig   (it, "TOTP" | "TOTP,BIO" | "TOTP,FIDO_CERTIFIED")
```

## 1차는 자사 조합 하나다

**구조는 처음부터 두되 값은 하나로 고정한다.** 1차 사용처가 모아라 본사라 분기할 환경이 없다.

```
자사 본사:  DMZ_RELAY · CAMERA · FCM · TOTP,BIO
```

플레이버 **틀을 먼저 만드는 이유**는, 나중에 고객사가 붙을 때 소스를 고치지 않고 값만
갈아 끼우기 위해서다. 틀 없이 자사용으로 박아 두면 첫 고객 납품에서 전부 걷어내야 한다.

## 고객 유형 → 빌드 조합 (고객사 납품 시)

| 고객 유형 | 망 | QR | 푸시 | 인증 |
|---|---|---|---|---|
| 일반 공사 (LTE 사용) | `DMZ_RELAY` | `CAMERA` | `FCM` | `TOTP,BIO` |
| **국방부**(카메라 차단) | `INTRANET` | `NONE` | `NONE` | `TOTP` |
| 카메라 허용 폐쇄망 | `INTRANET` | `CAMERA` | `NONE` | `TOTP,BIO` |
| FIDO 인증제품 요구 | `DMZ_RELAY` | `CAMERA` | `FCM` | `TOTP,FIDO_CERTIFIED` |

## 카메라 권한은 매니페스트를 나눈다

```groovy
case "CAMERA":
    flavor.buildConfigField "boolean", "FEATURE_QR", "true"
    project.android.sourceSets."${flavorName}".java.srcDirs += 'src/qr/camera/java'
    project.android.sourceSets."${flavorName}".manifest.srcFile 'src/qr/camera/AndroidManifest.xml'
    dependencies.add("${flavor.name}Implementation", "com.google.mlkit:barcode-scanning:...")
    break
case "NONE":
default:
    flavor.buildConfigField "boolean", "FEATURE_QR", "false"
    project.android.sourceSets."${flavorName}".java.srcDirs += 'src/qr/none/java'
    break
```

⚠️ **`<uses-permission android:name="android.permission.CAMERA"/>`를 `src/main`에 두면
`NONE` 빌드도 권한을 선언한 채 나간다** — MDM·보안 심의가 정확히 그것을 본다. 플레이버
매니페스트에 넣으면 보안 빌드 APK에는 권한이 아예 없어 **뜯어보면 증명된다.**

iOS는 `Info.plist`의 `NSCameraUsageDescription`을 같은 방식으로 스킴별로 나눈다.

## 앱의 능력을 서버에 알리는 방법

메뉴를 그리는 것은 네이티브가 아니라 **서버(Thymeleaf)**다. `BuildConfig.FEATURE_QR`은
네이티브만 안다. 웹뷰 User-Agent에 능력을 실어 보낸다.

```
User-Agent: ...(기존)... MOAApp/1.0 (caps=qr,push,bio)
```

서버가 이것을 읽어 메뉴를 결정한다([07](07-서버쪽-변경.md) P2). **API가 필요 없고**, 모든
웹뷰 요청에 자동으로 실리며, 접근 로그만 봐도 어느 빌드가 붙었는지 보인다.

**경계가 세 겹**: 빌드(권한 없음) · 앱(메뉴 없음) · 서버(경로 없음). 하나가 뚫려도 나머지가 막는다.

## 고객사별 앱 빌드 — 키는 고객사가 제공한다

실무 관행상 고객사가 FCM/APNs 키를 준다 = **앱 아이덴티티가 고객사 것**이다. 그래서 키를
여러 고객사가 나눠 갖는 문제가 애초에 없고, 모아라가 고객사 키를 보관할 필요도 없다.

**대신 빌드가 고객사별로 돈다.** 다음을 전부 빌드 변수로 빼 둔다.

```
번들 ID / 패키지명        com.고객사.moa
앱 이름 · 아이콘
서버 주소(DMZ FQDN)
google-services.json      (Android)
GoogleService-Info.plist  (iOS)
APNs .p8 + Key ID + Team ID   ← 푸시 릴레이 쪽
```

**소스에 한 줄이라도 박히면 고객사 수만큼 브랜치가 생긴다.**

⚠️ **iOS 서명은 고객사 Apple Developer 계정**이어야 한다. 보통 고객사 조직 계정에 개발자를
초대받는 형태인데, **계약 단계에서 이야기해 두지 않으면 배포 직전에 막힌다.**

### 고객사에 요청할 항목 (정형화해 둘 것)

| 구분 | 받아야 할 것 |
|---|---|
| FCM | 서비스 계정 JSON(프로젝트 ID 포함), `google-services.json` |
| APNs | `.p8` 키, Key ID, Team ID, 번들 ID |
| 서명 | Apple Developer 팀 접근 권한 또는 서명 절차 |
| 배포 | MDM 담당자·절차, 대상 단말 범위 |
| 망 | DMZ FQDN·인증서, 내부 서버 IP·포트, 방화벽 신청 창구 |
| **정책** | **카메라 허용 여부 · 폰의 망 접근(LTE/Wi-Fi) · 망분리 방식(물리/논리)** |
| 인증 | OTP·FIDO 인증제품 강제 여부 |

**마지막 두 줄은 계약 전에** 알아야 기능 범위를 약속할 수 있다.

## 키 수명 관리

푸시 키는 고객사 정책으로 주기 교체될 수 있다. 릴레이가 키를 이미지나 소스에 박지 말고
**환경변수/시크릿 파일에서 읽어 재기동만으로 반영**되게 한다 — 서버의 볼트 마스터키
(`MOA_VAULT_MASTER_KEY`)를 다루는 방식과 같은 원칙이다.
