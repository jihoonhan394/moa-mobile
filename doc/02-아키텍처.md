# 02. 아키텍처

## 왜 웹뷰 껍데기인가

서버가 **Thymeleaf SSR**이다 — 화면 89개, `@RestController` 0개, 인증은 세션 쿠키 + 2단계
진입(기관코드 → 로그인). 네이티브 앱을 만들면 UI를 다시 만들고 **API 계층을 새로 세워야**
한다(토큰 인증, DTO, 버전 관리).

웹뷰가 기존 세션 쿠키로 로그인하면 **모든 서버 호출은 이미 있는 화면들이 처리한다.**
네이티브가 할 일은 둘뿐이다.

| 네이티브가 하는 일 | 서버에 새로 필요한 것 |
|---|---|
| 푸시 토큰 등록 | 엔드포인트 **1개** |
| 카메라로 QR 스캔 | **0개** — 스캔 결과를 JS 브리지로 웹뷰에 넘기면 웹뷰가 기존 화면으로 처리 |

**토큰 인증 계층, DTO 규약, API 버전 관리가 전부 필요 없다.**

### 왜 Capacitor인가 (Expo·React Native가 아니라)

| | Capacitor | Expo / React Native |
|---|---|---|
| 기존 웹 UI | **그대로 쓴다** | 다시 만든다 |
| API 계층 | 불필요 | 필요 |
| 빌드 | **로컬**(Xcode / Android Studio) | EAS(클라우드)가 기본 |
| 코드베이스 | 하나(웹) | 둘(웹 + 앱) |

**결정적인 것은 빌드 위치다.** 고객사가 서명키·푸시키를 제공하는 구조([03](03-빌드와-환경.md))에서
**클라우드 빌드 서비스에 고객사 키를 올리는 것이 국방부·공사 보안 심의에서 걸릴 수 있다.**
Capacitor는 로컬에서 빌드한다.

> 공식 Claude Code 플러그인 마켓플레이스(315개)에 **Capacitor/Ionic 스킬은 없다.** `expo`
> 플러그인은 있지만 React Native용이다. **스킬이 있다는 이유로 아키텍처를 바꾸지 않는다** —
> 위 표의 비용 차이가 스킬 한 개보다 크다. 자세한 검토는 [06](06-작업방법.md) 참고.

### 애플 심사 리스크가 없다

순수 웹 껍데기 앱은 앱스토어 심사 4.2(minimum functionality)에서 거절된다. 그런데 이 제품은
**고객사 MDM 사내 배포**라 공개 심사를 거치지 않는다. 오히려 웹뷰 전략이 이 시장에서 더 안전하다.

(네이티브 푸시 + QR 스캐너가 있으니 공개 심사를 받더라도 통과 근거는 된다.)

## 구성도

```
             [인터넷 / LTE]
                   │
                  앱 (웹뷰 껍데기)
                   │ 443 TLS
                   ▼
┌──────────────── DMZ ────────────────┐
│  nginx 리버스 프록시                  │  인바운드. /m/** 화이트리스트
│  푸시 릴레이 (별도 프로세스)           │  아웃바운드 전용
└────────┬──────────────────▲─────────┘
         │ 443 재암호화       │ 443 mTLS
         │ (nginx IP만 허용)  │
┌────────▼──────────────────┴─────────┐
│              내부망                   │
│   MOA 앱서버 (Spring Boot)            │ ◀── 내부 PC 브라우저(관리자)
│    · 웹 UI(관리)  · /m/**(모바일)      │      ※ DMZ를 거치지 않는다
│    · 인증 · TOTP · 감사 · 볼트         │
│   PostgreSQL                         │
│   대상 서버들 (SSH/WinRM 제어 대상)     │
│   사내 SMTP                           │
└──────────────────────────────────────┘
```

**가장 중요한 선: 관리자 PC는 DMZ를 거치지 않는다.** 볼트·감사·사용자 관리 경로가 DMZ에
아예 존재하지 않는다. 같은 서버, 진입점 둘.

## 연결표 (방화벽 신청서에 그대로 쓸 수 있게)

| 출발 | 도착 | 포트 | 방향 | 비고 |
|---|---|---|---|---|
| 앱 (LTE/Wi-Fi) | DMZ nginx | 443 | 인바운드 | 경로 화이트리스트 |
| DMZ nginx | 내부 MOA | 443 | DMZ → 내부 | **nginx IP만** 허용 |
| 내부 PC 브라우저 | 내부 MOA | 443 | 내부망 내 | DMZ 미경유 |
| 내부 MOA | PostgreSQL | 5432 | 내부망 내 | |
| 내부 MOA | 푸시 릴레이 | 443 (mTLS) | 내부 → DMZ | 아웃바운드 |
| 푸시 릴레이 | FCM / APNs | 443 | DMZ → 인터넷 | **유일한 인터넷 아웃바운드** |
| 내부 MOA | 대상 서버 | 22 / 5985 / 5986 | 내부망 내 | SSH·WinRM 제어 |
| 내부 MOA | 사내 SMTP | 25 / 587 | 내부망 내 | 알림 메일 |
| 앱 ↔ OTP | — | — | **없음** | TOTP는 통신이 없다 |

**인터넷으로 나가는 구멍이 딱 하나(푸시 릴레이 → FCM/APNs)다.** 심의에서 설명하기 가장 좋다.

## 서버별 필요 여부 판정

| | 판정 | 근거 |
|---|---|---|
| **OTP 서버** | **불필요** | 서버에 `TotpService`(RFC 6238, Google Authenticator 호환)가 있다. TOTP는 공유 비밀 + 시각으로 양쪽이 각자 계산하므로 **서버-기기 통신이 없다.** 폐쇄망에 가장 잘 맞는다 |
| **API 서버** | **불필요** | 웹뷰가 세션 쿠키로 붙는다. 따로 두면 도메인·서비스를 쪼개야 하고 인증·감사·기관 스코프가 두 벌이 된다. 모바일 트래픽이 웹을 압도할 때 떼도 늦지 않다 |
| **웹서버(Apache 등)** | **불필요** | SSR이라 내장 톰캣이 웹서버다. nginx가 정적까지 프록시 |
| **푸시 릴레이** | **필요** | 엔드포인트 하나, DB 없음, 무상태. [05](05-푸시.md) |

⚠️ **TOTP의 운영 요구사항**: 허용 오차가 ±30초다. 내부망 서버가 NTP 없이 표류하면
**전 사용자의 2단계 인증이 한꺼번에 실패한다.** 내부 NTP가 필요하다.

## DMZ 중계 (nginx)

**애플리케이션 중계를 만들지 않는다.** 로직을 두 번 구현하면 버전이 갈라지고 DMZ에 비밀이
생긴다. 중계의 값어치는 전달이 아니라 **노출면 축소**에 있다.

### 경로 화이트리스트 — 모바일 전용 경로가 전제다

지금 URL을 그대로 열면 화이트리스트가 성립하지 않는다:

- `/solutions/**` → 상태 조회뿐 아니라 **제어(start/stop)까지** 열린다
- `/inventory/**` → QR 등록뿐 아니라 대장 전체·CSV 임포트가 따라온다
- 실수로 `/credentials/**`가 열리면 **볼트가 인터넷에 노출된다**

→ 서버에 **`/m/**`** 를 만든다([07](07-서버쪽-변경.md) P1).

```nginx
location ~ ^/(enter|login|logout)$ { proxy_pass https://internal; }
location /m/     { proxy_pass https://internal; }
location /css/   { proxy_pass https://internal; }
location /js/    { proxy_pass https://internal; }
location /fonts/ { proxy_pass https://internal; }

location / { return 404; }   # 그 외 전부 — 관리 화면은 DMZ에 존재하지 않는다
```

Spring Security에도 `/m/**` 규칙을 넣어 이중 방어한다(서버 `AGENTS.md`의 "URL 보안과 Service
레벨 이중" 원칙).

### ⚠️ X-Forwarded-For — 서버의 로그인 잠금이 여기 달려 있다

서버 `ClientIpResolver`는 XFF 체인에서 **첫 공인 IP**를 고른다. 그래서:

| 잘못된 설정 | 결과 |
|---|---|
| XFF를 안 넘김 | 모든 요청이 nginx IP 하나로 보임 → 누군가 20번 틀리면 **전체 사용자가 잠김** |
| `$proxy_add_x_forwarded_for`(덧붙이기) | 클라이언트가 보낸 XFF가 앞에 남음 → 값을 바꿔 가며 **IP 잠금을 완전히 우회** |

앞단이 nginx 한 홉뿐이면 **덮어써야** 한다:

```nginx
proxy_set_header X-Forwarded-For   $remote_addr;   # 덧붙이기 아님
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header Host              $host;
```

CDN/WAF가 한 겹 더 붙으면 `real_ip_module`로 신뢰 홉을 명시한다.

### 그 외 물릴 디테일

| 설정 | 값 | 이유 |
|---|---|---|
| `proxy_read_timeout` | **90s** | 솔루션 로그는 SSH로 최대 60초. nginx 기본이 딱 60초라 아슬아슬하게 502 |
| `client_max_body_size` | **25m** | 기본 1MB. 위키 첨부 20MB가 413으로 죽는다 |
| TLS | **두 구간 모두** | DMZ만 종료하고 내부를 평문으로 두면 심의에서 걸린다 |
| 내부 8081 방화벽 | **nginx IP만** | 내부망 어디서나 직접 붙으면 화이트리스트가 무의미 |
| 헬스체크 | `/login` → 302 | 서버 배포 스크립트가 이미 그렇게 쓴다 |

**앱은 Wi-Fi든 LTE든 항상 같은 주소(DMZ)로 붙인다.** "사내면 내부망 직결" 같은 최적화를
넣으면 origin이 갈려 **세션 쿠키가 따로 놀고 로그인을 두 번** 하게 된다. 한 홉 손해보다
단순함이 값어치 있다.

## 물리적 망분리 고객은 별도 옵션

DMZ에서 내부망으로 TCP 연결 자체가 안 되는 고객사라면 위 구성이 성립하지 않는다.
**설계를 바꾸지 말고 빌드 옵션을 바꾼다**([03](03-빌드와-환경.md)의 `applyNetworkConfig`).

`INTRANET` 빌드는 서버 주소가 내부망 직결이고, **푸시를 아예 빼고**(FCM SDK도 안 넣음)
앱 진입 시 폴링으로 간다.
