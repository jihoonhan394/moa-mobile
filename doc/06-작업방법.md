# 06. 작업방법

## 쓸 수 있는 스킬이 있는가 — 검토 결과

공식 Claude Code 플러그인 마켓플레이스(`anthropics/claude-plugins-official`, **플러그인 315개**)를
전수 검색했다. 키워드: `mobile · ios · android · capacitor · ionic · cordova · webview · pwa ·
react native · flutter · expo · swift · kotlin · xcode · apk · ipa · mdm · appium · detox`.

| 후보 | 무엇인가 | 우리에게 |
|---|---|---|
| **`expo`** | Expo 공식 스킬 — React Native 앱 빌드·배포·업그레이드·디버깅, Expo Router UI, EAS CI/CD, 스토어 배포 | **맞지 않는다** (아래) |
| `swift-lsp` | Swift 언어 서버(SourceKit-LSP) | 나중에 iOS 브리지 코드를 쓸 때 |
| `kotlin-lsp` | Kotlin 언어 서버 | 나중에 Android 브리지 코드를 쓸 때 |
| `firebase` | Firebase MCP — Firestore·auth·functions·hosting 관리 | 우리는 FCM만 쓰고 키는 고객사 것이다. 불필요 |
| `playwright` | 브라우저 자동화·E2E | 웹뷰 안의 화면을 테스트할 때 쓸 수 있다 |

**Capacitor / Ionic / Cordova / PWA 스킬은 없다.**

### `expo`를 쓰지 않는 이유 — 스킬 때문에 아키텍처를 바꾸지 않는다

Expo 스킬이 다루는 범위는 넓다(EAS 빌드, 스토어 배포, CI/CD, dev client 배포). 솔로 개발에서
그 부분이 가장 아픈 것도 맞다. 그런데:

| | Capacitor | Expo / React Native |
|---|---|---|
| 기존 웹 UI(화면 89개) | **그대로 쓴다** | 다시 만든다 |
| API 계층 | 불필요 | 필요(토큰·DTO·버전) |
| 코드베이스 | 하나 | 둘 |
| **빌드 위치** | **로컬**(Xcode / Android Studio) | EAS(클라우드)가 기본 |

**결정적인 것은 마지막 줄이다.** 고객사가 서명키·푸시키를 제공하는 구조에서
**클라우드 빌드 서비스에 고객사 키를 올리는 것이 국방부·공사 보안 심의에서 걸릴 수 있다.**

Expo도 로컬 빌드(`expo prebuild` + Xcode)가 가능하지만, 그러면 Expo 스킬이 다루는 가장 큰
부분(EAS)을 쓰지 않으면서 UI를 다시 만드는 비용만 지게 된다.

> **나중에 네이티브로 가기로 하면** `expo` 플러그인이 있다는 사실이 유용하다. 지금 기록해 둔다.

### 그래서 스킬은 언제 설치하나

| 시점 | 설치할 것 |
|---|---|
| 지금 | **없음.** 설계 단계라 코드가 없다 |
| 네이티브 브리지 코드를 쓸 때 | `swift-lsp` · `kotlin-lsp` |
| 웹뷰 화면 E2E를 붙일 때 | `playwright` |
| **첫 빌드가 성공한 직후** | **이 레포의 프로젝트 스킬을 직접 만든다** (아래) |

### 프로젝트 스킬을 직접 만드는 쪽이 맞다

Claude Code의 `run` 스킬은 **"프로젝트 스킬이 앱 실행을 다루고 있으면 그것을 따른다"**고
되어 있다. 모바일 빌드는 환경 의존이 크다 — Android SDK 경로, JDK 버전, Xcode 버전,
고객사별 플레이버, 시뮬레이터 띄우는 법.

**첫 빌드가 성공한 직후** 그 실제 명령을 `.claude/skills/`에 적어 두면, 이후 세션이 추측하지
않는다. 그때는 `/run-skill-generator`를 쓰거나 `skill-creator`로 만든다.

지금 만들면 **아직 검증되지 않은 절차를 적는 것**이라 오히려 해롭다.

## 개발 환경

| | |
|---|---|
| Node | LTS (Capacitor CLI) |
| Android | Android Studio + SDK, **JDK 17** (서버와 같은 함정 — `JAVA_HOME`이 JDK11로 잡혀 있다) |
| iOS | **집의 Mac Pro**에서 빌드·배포. ⚠️ 그 Mac의 Xcode 가능 버전을 먼저 확인해야 한다 → [08](08-결정-대기.md) 2번 |
| 서버 | 로컬 MOA(`D:\project\ai\moa`)를 `--spring.profiles.active=local`로 8081에 띄워 붙인다 |

**개발 PC는 Windows 11, iOS 빌드는 집의 Mac Pro다.** 코드는 한 레포에서 쓰고 iOS 빌드만
그 Mac에서 돈다. 클라우드 맥을 쓰지 않으므로 **서명키가 외부로 나가지 않는다.**

⚠️ **다만 그 Mac이 필요한 Xcode를 돌리는지 확인 전까지 iOS를 1차로 약속하지 않는다.**
오래된 Mac Pro는 최신 macOS를 못 올리고, 그러면 애플의 최소 SDK 요구를 못 맞춰
**빌드는 되지만 제출이 거부된다.** Android는 Windows에서 지금 시작할 수 있다.

## 프로젝트 초기화 (아직 하지 않았다)

```
moa-mobile/
├── doc/                  ← 지금 있는 것
├── www/                  ← 웹뷰가 처음 띄우는 로컬 자산(스플래시·오프라인 안내)
├── src/                  ← 네이티브 브리지 (푸시 등록 · QR · 생체)
├── android/
├── ios/
├── capacitor.config.ts
└── package.json
```

**웹뷰가 서버 화면을 쓰므로 `www/`에는 UI가 거의 없다.** 서버에 못 닿을 때 보여 줄 화면과
스플래시 정도다. 이게 Capacitor를 고른 이유의 실체다.

순서:

1. `npm init` → `@capacitor/core` · `@capacitor/cli` · `@capacitor/android` (`ios`는 macOS에서)
2. `capacitor.config.ts` — `server.url`을 빌드 변수로(고객사 DMZ FQDN)
3. 웹뷰 User-Agent에 `MOAApp/1.0 (caps=...)` 덧붙이기 ([03](03-빌드와-환경.md))
4. `android/app/secure_config.gradle` — kogas 패턴 이식, 플레이버 네 축
5. 서버에 `/m/**` 경로가 생긴 뒤 ([07](07-서버쪽-변경.md) P1) 실제 화면 확인

**3번을 빼먹으면 서버가 앱인지 모른다** — 메뉴가 PC용으로 나온다.

## 세션 쿠키가 웹뷰에서 유지되는지

가장 먼저 확인할 것이다. iOS `WKWebView`·Android `WebView` 모두 쿠키를 유지하지만:

- `SameSite` 설정과 origin이 맞아야 한다
- 서버에 `cookie.secure=true`가 켜지면 **HTTPS가 아니면 쿠키가 아예 안 실린다**
  → 로컬 개발에서는 평문 8081이므로 `secure`를 켜지 않은 상태로 먼저 확인
- 앱을 껐다 켰을 때 로그인이 유지되는지(세션 타임아웃 30분)

**이 확인이 1차 범위 전체의 전제다.** 안 되면 토큰 인증을 만들어야 하고, 그러면 설계가
크게 달라진다.

## 네이티브가 하는 일은 셋뿐이다

| | 무엇 | 서버와의 접점 |
|---|---|---|
| 푸시 토큰 등록 | FCM/APNs 토큰을 받아 서버에 올린다 | 엔드포인트 1개 |
| QR 스캔 | 카메라로 읽고 **JS 브리지로 웹뷰에 넘긴다** | 0개 (웹뷰가 기존 화면으로 처리) |
| 생체 서명 | nonce에 하드웨어 키로 서명 | 등록·검증 2개 |

**QR을 네이티브에서 서버로 직접 보내지 않는다.** 웹뷰에 넘기면 인증·감사·기관 스코프가
기존 경로를 그대로 탄다.

## 테스트

| 층 | 무엇 | 비고 |
|---|---|---|
| 서버 | 기존 JUnit 434개 | `/m/**` 화면도 서버 레포에서 테스트 |
| 네이티브 | 브리지 단위 테스트 | 플레이버별로 `NONE` 구현이 안전하게 비어 있는지 |
| 수동 | **카메라 없는 빌드에 QR 메뉴가 안 보이는지** | 경계 세 겹이 실제로 겹치는지 |
| 수동 | 세션 유지 · 푸시 수신 · 딥링크 | 실기기 |

**자동화하기 가장 어렵고 가장 중요한 것은 "꺼진 기능이 정말 꺼져 있는지"다.** APK를 뜯어
카메라 권한이 없는지 확인하는 절차를 릴리스 체크리스트에 넣는다.

## 릴리스 절차 (고객사별)

### 1차 (자사 본사)

```
1. 빌드                 Android: Windows에서 Gradle / iOS: Mac Pro에서 Xcode
2. 서명                 모아라 계정
3. 검증                 APK 권한 확인 · 꺼진 메뉴 확인 · 실기기 로그인·푸시
4. 배포                 Android: APK 직접 / iOS: TestFlight 내부 테스터(심사 없음)
```

**MDM이 필요 없다.** TestFlight 내부 테스터는 최대 100명까지 심사 없이 배포된다.

### 고객사 납품 시

```
1. 고객사 항목 수령      키·번들ID·FQDN·MDM 담당자 ([03](03-빌드와-환경.md) 체크리스트)
2. 플레이버 조합 결정     망·QR·푸시·인증 네 축
3. 로컬 빌드
4. 서명                 고객사 계정으로
5. 검증
6. MDM 전달
```

**4번이 일정의 병목이 될 수 있다** — iOS는 고객사 Apple Developer 계정 접근이 필요하고,
그 협의가 계약 단계에서 안 되어 있으면 배포 직전에 막힌다.

⚠️ **TestFlight는 고객사 폐쇄망에서 못 쓴다**(애플 서버 경유). 자사와 고객사의 배포 경로가
다른 것은 정상이다.

## 서버와의 작업 순서

이 앱은 서버 작업에 의존한다. **서버가 먼저다.**

```
서버: TLS/리버스 프록시(MVP B1)        ← 이 작업이 곧 DMZ 중계다
서버: /m/** 경로 + caps 읽기 (P1·P2)   ← 모든 모바일 화면의 토대
서버: XFF 덮어쓰기 확인 (P3)           ← 로그인 잠금이 여기 달렸다
──────────── 여기까지 되면 앱 착수 가능 ────────────
앱:   프로젝트 초기화 + 세션 유지 확인
앱:   1차 범위 1·3 (승인 처리 · 내 것 보기)
서버: step-up 게이트 (P6) + 앱: 2차 승인
서버: 기기 토큰 (P5) + 릴레이 + 앱: 푸시
서버: QR 코드 체계 (P8) + 앱: 스캔
```

**앱을 먼저 시작하면 붙을 화면이 없다.**
