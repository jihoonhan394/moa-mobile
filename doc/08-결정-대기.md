# 08. 결정 대기

**착수 전에 닫아야 하는 것들.** 위에서 아래로 갈수록 급하지 않다.

## ✅ 1. 첫 납품처 — 자사 본사 (2026-10-03 확정)

**1차 사용처가 모아라 본사다.** 이것이 가장 큰 단순화다.

| 그동안 막혀 있던 것 | 자사 본사라서 |
|---|---|
| 카메라 정책 | **우리가 정한다** |
| 망분리 방식(물리/논리) | **우리가 구성한다** — 논리 분리로 두면 DMZ 중계가 그대로 성립 |
| 폰의 망 접근 | 우리 환경이라 확인이 즉시 된다 |
| 푸시 키·서명 계정 | **모아라 계정 하나로 끝난다.** 고객사 키 수령·협의가 없다 |
| MDM 협의 | 자사라 불필요 |

**그래서 1차는 고객사별 플레이버 분기를 실제로 쓰지 않는다.** 구조는 둬야 하지만
([03](03-빌드와-환경.md)) 값은 자사 조합 하나로 고정한다:
`DMZ_RELAY` · `CAMERA` · `FCM` · `TOTP,BIO`.

### 더 중요한 이득 — 실사용 경험이 쌓인다

서버 쪽 MVP 문서의 가장 약한 항목이 **"실사용 경험 없음"**이었다. 자사에서 먼저 쓰면
고객 납품 전에 그것이 메워진다. **앱의 1차 목표를 "고객에게 팔 기능"이 아니라
"우리가 매일 쓰면서 고칠 것"으로 두는 편이 맞다.**

→ 1차 범위([01](01-개요와-범위.md))에서 **승인 처리와 내 것 보기**를 먼저 내는 이유가
여기서 더 분명해진다. 전 직원이 매일 쓴다.

## ✅ 2. iOS 빌드 — 집의 Mac Pro (2026-10-03 확정)

iOS 빌드·배포를 그 Mac에서 진행한다. 클라우드 맥 임대를 피할 수 있어
**서명키가 외부로 나가지 않는다**(심의에 유리하다).

### ⚠️ 먼저 확인해야 하는 것: 그 Mac이 필요한 Xcode를 돌릴 수 있나

오래된 Mac Pro는 **최신 macOS를 올리지 못할 수 있고**, 그러면 Xcode 버전이 막힌다.
애플은 앱 제출 시 **최소 SDK 버전**을 요구하므로, Xcode가 너무 낮으면 **빌드는 되지만
제출이 거부된다.**

확인 순서:

1. ` > 이 Mac에 관하여` → **모델 식별자**(예: `MacPro6,1`)와 **macOS 버전**
2. 그 macOS에서 설치 가능한 **최대 Xcode 버전**
3. 그 Xcode가 **현재 애플이 요구하는 최소 SDK**를 만족하는지

| 결과 | 대응 |
|---|---|
| 충분하다 | 그대로 진행 |
| macOS는 올릴 수 있다 | 업그레이드 후 진행 |
| 하드웨어가 막는다 | **Android 먼저 내고 iOS는 2차** — 자사 본사라 단말 구성을 우리가 알고, Android 비중이 높으면 문제가 되지 않는다 |

**이 확인 전까지 iOS를 1차 범위로 약속하지 않는다.**

### 자사 배포 경로는 고객사와 다르다

| | 자사 본사 (1차) | 고객사 (나중) |
|---|---|---|
| iOS | **TestFlight 내부 테스터**(최대 100명, 심사 없음) 또는 Ad Hoc | 고객사 MDM |
| Android | APK 직접 배포 | 고객사 MDM |

**TestFlight는 애플 서버를 경유한다** — 자사에서는 괜찮지만 **고객사 폐쇄망에서는 못 쓴다.**
즉 배포 경로가 두 가지가 되고, 그건 정상이다. 1차에 MDM을 붙일 필요는 없다.

## ✅ 3. 레포 구성 — 별도 git 레포 (2026-10-03 확정)

레포 이름 **`moa-mobile`**. 서버 레포 `moa`와 나란히 읽히고, 새로 보는 사람이 묻지 않고 찾는다.

앱 릴리스 주기가 서버와 다르고 고객사별 빌드 설정을 앱 쪽에만 둘 수 있다. 서버의 `/m/**`
변경과 앱 변경이 따로 추적되는 것은 감수한다 — 그 둘은 실제로 다른 속도로 움직인다.

**푸시 릴레이는 이 레포에 둔다.** DMZ에 올라가는 산출물이고 서버 jar와 수명이 다르다.
서버 레포의 Gradle 서브프로젝트로 두면 서버 빌드가 DMZ 산출물까지 끌고 간다.

## 🟡 4. 알림 방식의 기본값

푸시가 안 되는 고객이 있다([05](05-푸시.md)). 기관별 설정으로 두기로 했는데 **기본값**을 정해야 한다.

- 푸시 먼저, 안 되면 메일로 떨어뜨리기
- 또는 기본은 메일, 푸시는 명시적으로 켜기

**후자를 권한다** — 폐쇄망 고객이 다수라면 기본값이 동작하지 않는 상태로 납품되는 것이 나쁘다.

## 🟡 5. 오프라인 큐잉을 할 것인가

창고·서버실은 Wi-Fi가 안 잡히는 경우가 흔하다. QR 스캔과 입력을 로컬에 쌓아 두고 나중에
동기화할지 정해야 한다.

| | |
|---|---|
| 안 한다 | 현장에서 신호가 없으면 작업을 못 한다 |
| 한다 | **웹뷰만으로는 까다롭다** — 네이티브 저장소와 동기화 로직이 필요하다. Capacitor가 필요한 두 번째 이유가 된다 |

**실사(2차)를 할 거면 사실상 필요하다.** 1차에서는 미루고, QR 코드 체계를 설계할 때
"나중에 큐잉이 붙는다"는 전제만 남긴다.

## ⚪ 6. QR 스티커 체계

[07](07-서버쪽-변경.md) P8과 서버의 M-I02를 함께 설계할 때 정한다.

- 코드 길이·문자 집합·체크섬
- 인쇄 규격(라벨 크기·수량)
- 스티커를 미리 대량 발급할지, 자산 등록 시 발급할지
- **한 번의 스캔이 조회와 등록을 겸하게** 할지(등록 안 된 코드면 등록 폼, 등록된 코드면 조회)

마지막 항목을 권한다 — 사용자가 "등록 모드/조회 모드"를 고를 필요가 없다.

## ⚪ 8. 조달 요구사항에 "FIDO 인증 제품"이 들어오는 고객이 있나

있으면 그 고객만 `FIDO_CERTIFIED` 플레이버로 붙인다([04](04-인증과-승인.md)).
없으면 자체 구현(하드웨어 키 + 생체)으로 충분하다.

`kogas` 프로젝트에 드림시큐리티 MagicFIDO를 붙인 이력이 있어 **실제로 요구하는 고객이
있었던 것 같다** — 확인이 필요하다.
