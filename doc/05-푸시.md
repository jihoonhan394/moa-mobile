# 05. 푸시

## 방향 — 내부망이 릴레이를 부른다

```
내부망 앱서버 ──(outbound 443 mTLS)──▶ 푸시 릴레이(DMZ) ──▶ FCM / APNs ──▶ 폰
```

이 방향이어야 하는 이유는 망 정책이다. **내부망에서 DMZ로 나가는 연결은 대개 허용되지만,
DMZ에서 내부망으로 들어오는 연결은 막히거나 까다롭다.** 릴레이가 내부망에 뭘 물어보러 오는
구조를 만들면 심의에서 걸린다.

그래서 푸시 릴레이는 **받기만 하는 싱크**다. 내부망에 아무것도 요청하지 않는다.

## 폐쇄망에서는 푸시가 안 올 수 있다

릴레이는 서버→FCM 문제를 해결한다. 그런데 **FCM→폰**은 폰이 구글·애플에 닿아야 한다.

| 상황 | 푸시 |
|---|---|
| 폰이 LTE에 있다 | ✅ 온다 |
| 폰이 사내 Wi-Fi(인터넷 없음)에 있다 | ❌ 안 온다 |
| 보안 정책이 외부 경유를 금지한다 | ❌ 못 쓴다 |

그리고 함정이 하나 더 있다 — **푸시를 받는 것과 앱을 쓰는 것은 다른 문제다.**
LTE로 푸시를 받아도, 눌러서 앱을 열면 내부망 서버에 못 닿는다(DMZ 중계가 없으면).

**→ 알림 방식을 기관별 설정으로 둔다**: 푸시 / 메일 / 앱에서 확인.
푸시가 안 되는 기관도 앱을 쓸 수 있어야 한다.

## 무내용 원칙

```
푸시 본문:  "새 알림 1건"        ← 구글·애플을 지나는 전부
앱을 열면:  실제 내용을 내부망 서버에서 가져옴
```

*"A4용지 요청이 승인되었습니다"* 같은 문장을 푸시에 담으면 그것이 DMZ를 지나
**구글·애플 서버를 경유한다.** 국방부·공사 심의에서 걸리는 지점이다.

**고객사가 FCM 프로젝트를 소유하면 콘솔에서 발송 내역을 본다** — 무내용이면 볼 게 없다.
"우리 프로젝트, 우리 키, 내용 없음"이 심의에 가장 유리하다.

## 릴레이 API

```
POST https://push.고객사.dmz/api/v1/send        (mTLS)
Content-Type: application/json

{
  "messageId": "b3f1...",            // 중복 발송 방지 키
  "tokens": ["fcm:...", "apns:..."], // 내부망이 갖고 있다가 이때만 넘김
  "title": "MOA",
  "body": "새 알림 1건",              // ← 구글·애플을 지나는 전부
  "badge": 3,
  "ref": "9c2a..."                   // 알림 행 id (의미 없는 UUID)
}
```

응답:

```json
{
  "sent": 2,
  "failed": [ { "token": "fcm:...", "reason": "UNREGISTERED" } ]
}
```

`ref`는 의미 없는 UUID라 그것만 보고는 아무것도 알 수 없고, 앱이 내부망에 물어야 목적지를 안다.

## 죽은 토큰 회수 — 응답으로 돌려받는다

앱을 지운 기기는 FCM이 `UNREGISTERED`를 돌려준다. 그걸 내부망이 알아야 지운다.
그런데 릴레이는 내부망을 부를 수 없다.

**→ 발송 호출을 동기로 두고 응답에 실패 목록을 담는다.** 신뢰 방향(내부망 → DMZ 단방향)을
깨지 않고 회수된다.

## 기기 토큰은 내부망에 둔다

FCM 토큰은 "어느 기관의 누가 어떤 기기를 쓰는지"를 드러내는 자산이다. **DMZ 릴레이에
상주시키지 말고** 내부망에 저장했다가 발송 시점에만 넘긴다. 릴레이는 상태 없이 통과만 시킨다.

## 재시도와 중복

릴레이가 잠깐 죽으면 내부망이 재시도해야 하는데, 그때 같은 알림이 두 번 가면 안 된다.
`messageId`를 릴레이가 짧게 기억(수 분)하고 같은 것은 무시한다.

## 릴레이는 얼마나 큰가

**아주 작다.** 엔드포인트 하나, DB 없음, 상태 없음.

1. mTLS 검증
2. `messageId` 중복 확인 (메모리 캐시면 충분)
3. FCM v1(OAuth 토큰 발급) / APNs(JWT 서명) 호출
4. 결과 취합해서 응답

**별도의 작은 서비스로 둔다.** 서버 jar를 프로파일로 나눠 DMZ에 올리는 방법도 있지만,
그러면 DB 드라이버와 컨트롤러 55개가 통째로 DMZ에 놓인다 — 심의에서 "DMZ에 전체
애플리케이션이 있다"로 읽힌다.

레포 위치는 결정 대기다([08](08-결정-대기.md)).

## 무엇을 푸시할까

| 알림 | 즉시성이 필요한가 |
|---|---|
| **솔루션 상태 이상** | ✅ 가장 필요하다 |
| 접근 요청 도착(승인자에게) | ✅ 요청자가 기다린다 |
| 소모품 요청 결과(요청자에게) | 🔸 메일로도 충분 |
| 만료 임박 | ❌ 메일·인앱이 낫다 |
| 인수 확인 요청 | 🔸 |

**푸시가 안 되는 고객에서는 전부 메일+인앱으로 떨어진다.** 그래도 기능이 죽지 않게 설계한다.
